# Layer 2 公开研究执行 SOP

这是 [find-channels](../SKILL.md) 的执行参考，适用于任何具备相应访问权限的 Agent。执行者、模型、浏览器和登录工具由使用者按实际能力选择，不是数据架构或流程的前提。公开资料按所属公司保存，不因工具、采集者或尚未申请职位而转入私人 inbox。

## 执行顺序

1. 读取仓库 `AGENTS.md`、渠道 Skill 和 `data/index.json`，确认本次公司与平台范围。
2. 查找公开企业主页并核实主体，保留稳定 ID、真实观察日期、页面依据及公开属性；公司规模或名称相似不足以确认归属。
3. 采集 Agent 直接更新所负责的 `data/companies/<id>.json`：入口进 `channels`，证据进 `sources`，新增渠道证据用 `scope: "channel"`。可直接编辑，或将纯公共观察 JSON 经标准输入交给 `update_layer2.py --apply`。
4. 重新生成索引和阅读版，运行仓库校验，报告已更新项与未找到、受限、归属存疑项。无需初始化私人工作区、生成私人批次或等待管理 Agent 再搬运。

## 给任意采集 Agent 的任务模板

```text
请在任务指定的 cn_ai_opp 仓库中，先读 AGENTS.md 和 skills/find-channels/SKILL.md，以 data/index.json 中全部公司为清单，仅查找并核实 BOSS直聘、猎聘上的公开企业主页；将已核实结果直接写入 data/companies/<id>.json 的 channels 和 sources，记录主体归属与实际核查日期，保留原业务资料和核查日期；未找到、打不开或主体存疑的逐项报告，不猜链接、不伪造 confirmed，不写私人 inbox 或 applications，完成后生成阅读版并运行检查，不发送消息或投递。
```

模板中的平台和公司范围随用户任务调整；这份两平台示例不要求采集脉脉。具备仓库写入能力的 Agent 直接维护公司档案；只有客观上无法访问仓库时，才回传纯公共 JSON 观察结果供有权限的 Agent 写入，这不建立私人 inbox 流程。

## 资料边界

- 企业主页归 `channels`；公开岗位事实仍归公司研究，不能把具体 JD 当企业主页。岗位明细按公共数据契约保存，不因尚未投递而建立个人申请日志。
- 查不到不是确定没有招聘；访问失败和同名主体冲突分别说明，不补造证据或刷新未访问页面的日期。
- 个人聊天、HR 私人联系方式、简历、个人薪酬期望与申请状态只进入私人 applications 流程。网站公开的岗位薪资范围属于公开岗位事实。
- 多 Agent 按公司划分写入责任，同一公司由一个写入者汇总；写入前检查并发变更，不能覆盖他人已更新的记录。
